RSS expectation: the compiled document and its node count are unchanged, so the dominant tier RSS stays as measured. What is deferred is one font-size style property per node actually shown. A default tier-1 window (~110x30 cells) writes about 3,300 of 6,144 slots, leaving ~2,800 overrides unallocated; a tier-2 window with ~150x50 cells writes about 7,500 of 18,432, leaving ~11,000. At tens of bytes per override that is a sub-MB, proportional saving, not a multi-MB one, and it needs a scoped RSS A/B before any perf claim. The other apparent cut - dropping the per-slot `-` text placeholder - is rejected: `set_text_ref` requires a single text child and the compiler drops whitespace-only text (`render-core/model/document.rs:415-427`, `render-compiler/html.rs:56-58`), so removing it breaks every text write. Settings/search/tabs overlay state (search bar, settings view, rename, menu) is already built on first use, and deferring the command-history trie was declined in u21.

PARTIAL - The smallest safe cut is implemented: per-node font-size projection is now lazy, written only when a run node first becomes visible, so unused and overlay-only pool slots no longer retain a document style override from launch. Settings/search/tabs overlays reuse the same run nodes, so there is no separate overlay node tree to build; true lazy node creation is blocked by the fixed compiled document schema. Three production edits, all in `crates/flamewm-terminal/src/ui.rs`, are UNBUILT because the brief forbids cargo; the orchestrator must build and run terminal tests. Visuals are pixel-identical by final-state equivalence, not by executed proof, and the RSS benefit remains an estimate pending a scoped A/B measurement.
