# UI/UX Consistency Audit

Scope: `ui/**` HTML/CSS as compiled by `flamewm-render-compiler` (via `include_str!`), settings toggle wiring, and dead CSS. Base: `6aa187a9`.

## Method and limits

- Static: pseudo-state support in `crates/flamewm-render-compiler/src/css.rs`, `:focus`/`:disabled` grep over `ui/`, class-reference scan of every CSS class against `ui/**/*.html`, `ui/**/*.js` and `crates/**/*.rs`, settings key to Rust consumer trace.
- Runtime: not run in this pass. No hover, focus or theme screenshots were taken. Visual claims below are unverified.
- Not covered: colour-token tidy-up across all apps, radius/spacing normalisation, tooltip coverage, scroll behaviour, truncation, and `.vendor/cosmic-*` comparison. These are open.

## Findings

### F1. No keyboard focus state exists anywhere (partly fixed in Pass 5: compiler, codec, owner, ring; app wiring open)

- `:focus`, `:focus-visible` and `:disabled` appear in zero UI stylesheets.
- The render compiler accepts only `:hover`, `:active`, `:root` (`css.rs:323-326`). Any `:focus` rule would fail compilation with `unsupported pseudo-class`.
- Only 3 `<input>/<select>/<textarea>` elements exist in `ui/**/*.html` and one `tabindex` in `ui/settings.html`.
- Disabled looks come from `.disabled` / `.is-disabled` classes only (`.media-control.is-disabled` opacity 0.4 is the one clear case).
- Fix needs a `:focus` pseudo-state in `flamewm-render-compiler` and a focus signal from the shell/UI owner. Not changed in this pass.

### F2. Dead CSS rules (fixed)

Each class was confirmed absent from all HTML, JS and Rust sources (`rg -w`) before removal:

| File | Removed | Note |
| --- | --- | --- |
| `ui/explorer/explorer.css` | `.place-dot` | no reference |
| `ui/task-manager/task-manager.css` | `.dangerous` | no reference |
| `ui/settings.css` | `.display-card .setting-block` | `display-card` no reference |
| `ui/shell/flamewm.css` | `.selected-monitor` | no reference (the root prototype copy is left, see F5) |
| `ui/shell/flamewm.css` | `.network-actions`, `.popup-tabs` from the `.audio-row` selector list | `popup-tabs` appears only as a canary scenario name, not as a class |

Kept on purpose: `.is-selected`, `.is-current` (generated in `crates/flamewm-settings/src/view.rs`), `widget-analog-n*`/`widget-edge-*` (generated by name in `ui/desktop` and render code), `pal-*` (generated palette classes).

### F3. Settings toggle without behaviour (resolved: removed)

- `settings.toggle.lockOnSuspend` had no runtime reader. Wiring a logind `PrepareForSleep` subscription needs a change in `flamewm-wm-wayland/src/logind.rs` (1590 lines, owned by session code), so the dead toggle was removed instead: platform field/default/parse entry, settings actions/consts/app mapping, the `ui/settings.html` row and the controller test entry.
- Legacy files: the settings parser stores unknown keys in `unknown_keys` and never rejects them, so an old `lockOnSuspend=false` line is kept verbatim and ignored (`crates/flamewm-platform/src/settings/tests.rs`, `legacy` lock-file test).
- Other settings toggles checked by non-test readers: `lockShowDate`/`lockShowUsername` (`crates/flamewm-lock/src/settings.rs`), `assistant.speechToText`/`textToSpeech` (`crates/flamewm-assistant/src/lib.rs`), `showContentWhileDragging` (`flamewm-wm-x11`), `pointerRawInput` (`flamewm-wm-wayland/src/drm/input.rs`) all have live consumers.
- Not checked: whether each consumer re-applies the value live without restart. Needs runtime verification.

### F4. Theme and contrast (partly resolved)

- Resolved: built-in accent tokens (`--accent`, `--accent-soft`, `--accent-strong`, `--preview-outline`, `--snap-fill`, `--desktop-hover`, `--desktop-hover-border`, `--desktop-selected`, `--desktop-selected-border`) are seeded in `builtin_color_tokens()` in `crates/flamewm-render-compiler/src/compile.rs`. The sheet `:root` overrides them by name. The literal copies were removed from 7 sheets. Test: `builtin_accent_tokens_resolve_without_root_and_root_overrides_them`.
- Not added: built-in hover/active/focus tokens. No `:hover`-derived token set or focus state exists yet (see F1), so there is no value to default to.
- Open: the accent tints are fixed to the default accent. Live Settings overwrite only `--accent` (assumed; not runtime-verified), so tints do not follow a custom accent.
- `ui/flamewm.css` and `ui/shell/flamewm.css` define only a dark token set on `:root`. No `prefers-color-scheme` or light token set exists, so light-theme contrast is not applicable today.
- A global text-shadow gate exists (`ui_text_shadow` in `flamewm-render-core/src/paint.rs`), so the opt-out is code-level, not per-element.
- Hard-coded surface fills are common and bypass tokens: `#292c2f` (`.nav-row:hover`), `#3b3f43` (`.title-button:hover`), `#303438`/`#383c40` (settings buttons), `#25282b`/`#272a2d`. Tokenising these is open.

### F5. Duplicate and orphan stylesheets

- `ui/flamewm.css` (root) is not included by any runtime `include_str!`. It backs the prototype `ui/index.html`, which `FINISH_LINE_VERIFICATION.md`, `tools/ui_contract_guard.py` and `tools/accent_default_guard.py` reference. It is a parallel copy of `ui/shell/flamewm.css` and has drifted. Not removed, because tooling depends on it.
- `ui/desktop/index.html` and `ui/shell/*` are runtime sources.

### F6. Pre-existing guard failures (not introduced here)

- `tools/ui_contract_guard.py`: 1 error (`surface_border_opacity default != RIM_PERCENT`, a platform default mismatch), 22 warnings.
- `tools/accent_default_guard.py`: FAILED with 14 hardcoded default accents at the time of the audit. Now passes: the default lives in `crates/flamewm-api/src/settings.rs`, which the guard allows as its owner.
- Ran after the F2 edits. The failing lines are outside the deleted rules. Not re-run at `HEAD`.

## Pass 4: neutral tokens route through the appearance palette

Scope: shell and task-manager neutral colours. Base: `origin/main` after `5bb1133b`.

### Fixed

- `flamewm_ui_core::glass::palette_from_settings(snapshot)` is the single selector: `appearance=light` gives `Palette::LIGHT`, every other value gives `Palette::RWR_0_0_9`. Shell and task-manager both call it.
- `ui/shell/flamewm.css`: 12 literal uses of `#202326`, `#1b1e20`, `#aeb4bb`, `#f1f2f3` (the surface, panel/sidebar, muted and text values) became `var(--surface|--panel|--muted|--text)`. The `:root` line keeps the shipped Dark values, so Dark output is unchanged.

Dark writes equal the `:root` defaults, and `set_color_variable` is a no-op when the value is unchanged, so no extra repaint. Tokens a surface does not compile are skipped.
- `crates/flamewm-task-manager/src/lib.rs` `paint_theme` projects `--text` and `--muted` from the palette. Before this, light glass put light-on-light text in the task manager.
- `ui/task-manager/task-manager.css` `:root` `--text` and `--muted` now equal `Palette::RWR_0_0_9` (`#f1f2f3`, `#aeb4bb`; was `#f2f3f5`, `#a9acb2`). This is a 1-step Dark change on those two tokens.
- Tests: `glass::appearance_golden_tests::neutral_palette_tokens_follow_appearance`, `settings_projection::tests::neutral_tokens_project_light_palette_and_dark_defaults`, `context_menu::css_contract_tests::shell_neutral_surfaces_use_palette_tokens` (fails if any of the four literals returns outside `:root`).

### Left open (with reason)

- F1 `:focus` / `:focus-visible` (not fixed). The compiler accepts only `hover`, `active`, `root` (`css.rs`). Adding a focus state needs: a `PseudoState::Focus` and a `focus_style` field on `CompiledNode` (about 40 struct-literal sites across render-core, render-x11, lock, ui-document, ui-x11); a `FORMAT_VERSION` bump in `render-core/src/codec.rs` (v8 to v9, with a legacy decode path); a `focus` field in `InteractionState`; and a keyboard focus owner. No Tab traversal or focus model exists in the UI runtime for shell, settings, explorer, task-manager or finder, so the ring would have no trigger. Needs its own pass with runtime proof.
- F1b `:disabled` (not fixed). Not a supported pseudo-class. `.is-disabled` is class-based (`.media-control.is-disabled` opacity 0.4 is the one case). A static `[disabled]` match is possible in the compiler, but it still needs a style slot and token set, so it is not started here.
- Light hover fill. `--hover-fill:#ffffff40` (shell root) is white alpha, so it is nearly invisible on the light panel. Needs a light-token pair; not verified visually.
- Remaining shell literals (about 60 sites: `#303438`, `#272a2d`, `#17191b`, accent-state colours, status colours). Not tokenised: each needs a semantic name and a light value.
- Hover/pressed consistency with the titlebar inversion (item 4). The titlebar state lives in `crates/flamewm-wm-wayland` and `crates/flamewm-wm-x11`, which this pass did not touch. Not audited.
- Explorer, finder, settings: no `--text`/`--muted` projection changed here. Their palette literals (see Pass 2 table) are open.
- Not visually verified. No light or Dark screenshot was taken in this pass. Contrast of the new light text tokens on the shell glass is covered only by the existing `Palette::LIGHT` contrast tests in flamewm-skin, not by rendered output.

## Pass 5: keyboard focus (partial)

Scope: `:focus-visible` pseudo-state, shared focus owner, shared ring token. Base: `origin/main` after `c060e2ae`.

### Fixed

- `flamewm-render-compiler/src/css.rs`: `:focus` and `:focus-visible` parse to `PseudoState::Focus`. Other pseudo-classes still fail with `unsupported pseudo-class`.
- `compile.rs`: each element computes a focus style and stores it in `CompiledNode::focus_style` only when it differs from base, like hover and active.
- `flamewm-render-core`: `CompiledNode::focus_style: Option<Arc<Style>>` (about 45 construction sites, all `None` except the compiler). `InteractionState::focus: Option<u32>`. `style_for` precedence is active, focus, hover. `damage.rs` treats a focus style with non-absolute position as a geometry change, like hover and active.
- Codec: `FORMAT_VERSION` 8 to 9. `FORMAT_VERSION_FOCUS_LEGACY = 8` decodes with `focus_style: None`. Legacy fixtures use `encode_version` at their own version. Stale `FORMAT_VERSION == 8` guards are now 9. The unknown-version test uses 10.
- `flamewm-render-compiler` built-in token `--focus-ring` is derived from the accent (`tint(0xff)`), next to `--accent`.
- `ui/base/base.css`: `button/.nav-row/.segment/.settings-button/.select-box/.step-button/.toggle/.accent-swatch/.hotkey-key/.mode-slot:focus-visible { border-width:1px; border-color:var(--focus-ring) }`. `button` sets `border-width:0` globally, so the width must be restated.
- `flamewm-ui-document/src/focus.rs`: `FocusOwner` (one per document). `handle_key` takes Tab / Shift+Tab (`ISO_Left_Tab`) for document-order traversal with wrap-around, and Enter / Return / KP_Enter / space to return `FocusKey::Activate(index)`. The caller dispatches that node's `data-action`. `apply` writes into `InteractionState::focus`. A focusable node is an element with non-empty `data-action`.

### Tests

- `flamewm-render-compiler`: `focus_visible_and_focus_compile_to_focus_style`, `focus_ring_token_is_builtin_accent_derived`.
- `flamewm-render-core` codec: `v9_roundtrip_preserves_focus_style`, `v8_document_decodes_without_focus_style`.
- `flamewm-ui-document::focus`: traversal forward and backward, wrap, no-focusable documents, owner key handling, `set` rejecting non-focusable targets.

### Not done (open)

- App wiring (no app is end-to-end yet). The UI window runtime lays out with `InteractionState::default()` (`crates/flamewm-ui-x11/src/surface_runtime.rs:652,776,791`), so no interaction state reaches UI windows. `UiDocumentAccess` (`crates/flamewm-ui-document/src/template.rs:113`) exposes text and image setters only, not the compiled document. Keys reach `handle_key_event` as `UiKeyEvent` (`crates/flamewm-ui-x11/src/lib.rs:243`) without the document. Follow-up: store a `FocusOwner` and an `InteractionState` in the ui-x11 surface runtime, call `FocusOwner::handle_key` before the controller on `UiControllerEvent::Key`, dispatch `action_for` on `Activate`, and repaint when focus changes. Then wire `flamewm-settings` first.
- `:disabled` (F1b) is still not a pseudo-class. It needs a second style slot plus an attribute match, so it was not cheap in this pass.
- Focus visibility in `ui/shell`, `task-manager`, `explorer`, `finder` and `terminal` css: not added. Only `ui/base/base.css` (shared) and the settings selectors got the ring rule.
- Visual result of the ring: unverified. No runtime or screenshot run was done.

## Pass 6: keyboard focus wired end-to-end (archiver)

Scope: the Pass 5 "App wiring" follow-up for one app. Archiver was chosen because its only keys are Up/Down/PageUp/PageDown/Escape, it has no text input, and its controls are `data-action` buttons that already handle `Press`.

### Fixed

- `flamewm-render-core` `RuntimeDocument`: `focus: Option<u32>` with `focus()` / `set_focus()`. The document is the single store; the focus owner is rebuilt from it per key.
- `flamewm-ui-document` `UiDocument::with_keyboard_focus()`: opt-in per window. `into_parts` now returns a fourth flag. Windows without the flag keep every key unchanged.
- `flamewm-ui-x11` `route_focus`: when opted in, Tab / Shift+Tab move focus and are consumed (also when focus does not move, so Tab never reaches the window). Enter / Return / Space on a focused control deliver a synthesized `Press` of its `data-action`. Other keys and all releases pass through unchanged.
- `flamewm-render-x11` `sync_keyboard_focus`: after the typed-key action fires, `InteractionState::focus` is copied from the document. A change calls `mark_input_repaint`, the same input path hover uses, so the damage planner redraws the focus ring region only. No timers and no idle wakes are added.
- `flamewm-ui-document::focus`: `handle_key` now also matches `"Space"`. X11 canonical naming (`events.rs` `canonical_key_name`) sends `Space`, so the owner previously missed the key.
- `flamewm-archiver-app` opts in with `with_keyboard_focus()`.
- Architecture guard: `focus.rs` named `flamewm_render_core` paths directly (`renderer-symbol`, from Pass 5, failing `tools/architecture_guard.py` on `main`). It now imports the types from the `flamewm-ui-document` crate root, which re-exports them under the existing `lib.rs` exception. No exception entry was added. Commit `0f608421`.

### Deliberately unchanged

- `surface_runtime.rs` intrinsic measures (`measure_node_outer_intrinsic_device_size`, `document_space_extent`, `default_layout`) keep `InteractionState::default()`. Focus must not change intrinsic size. Otherwise Tab could resize the window, which would then re-measure and loop. Paint and the render layout path do receive focus.
- `:disabled` (F1b) is not started. It needs `PseudoState` support, a second style slot on `CompiledNode` (about 45 construction sites), a codec version bump, and an attribute value carried into the compiled node. That is too large for this pass. It stays open.

### Tests

- `flamewm-ui-x11` `route_focus` tests: `tab_walks_focusable_controls_in_order_and_writes_document_focus`, `enter_and_space_activate_the_focused_control_only`, `non_focus_keys_and_releases_pass_through_unchanged`, `window_without_focusable_controls_consumes_tab_and_keeps_no_focus`.
- `flamewm-ui-document::focus`: `owner_moves_activates_and_writes_interaction_focus` now also asserts `Space`.

### Not run

- No runtime or screenshot run. The focus ring paint, the damage region size, and whether `border-width:1px` on focus changes button layout (base.css `button` sets `border-width:0`) are unverified. Run archiver under Xvfb, Tab through `ar.*` rows, and check the ring and the redraw region before claiming the visual result.
- Other apps (task-manager, explorer, settings, finder) are not opted in. Each has modal key handling (task-manager search, settings hotkey and slider capture, terminal raw input) that needs its own review before Tab / Space routing is safe.

## Pass 11: focus ring on screen (archiver, settings), root cause of the Pass 9 failure

### Root cause of the Pass 9 "no ring"

- The Pass 9 binary was built from `c3814f8d`. That commit predates the focus wiring (`5df5e26d` ui-x11 `route_focus`, `e5a36fa0` archiver opt-in, `sync_keyboard_focus` in `flamewm-render-x11`). - Current main is wired end to end, checked in code: `flamewm-render-x11/src/app/events.rs` `KEY_PRESS` calls `emit_typed_key` then `sync_keyboard_focus` (`render.rs`), which copies `RuntimeDocument::focus()` into `InteractionState::focus` and calls `mark_input_repaint`. `style_for` applies `focus_style` when `focus == index`. The compiler emits `focus_style` for `:focus-visible`.
- No "focus-visible heuristic" exists. The ring shows exactly when `InteractionState::focus` is set, so it appears after Tab and never on click.

### Fixed

- `flamewm-settings/src/view.rs`: `document()` and `document_with_backdrop()` opt in with `with_keyboard_focus()`. Settings' existing `base.css` ring (`button:focus-visible`) covers its `<button data-action>` controls; no CSS change.
